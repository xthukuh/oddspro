# Instant date navigation: client-side records cache

> **For agentic workers:** this is a small hotfix, ONE commit. Read the whole file, then implement. Steps use checkbox (`- [ ]`) syntax.

**Goal:** flipping to a date you have already opened paints instantly, with no loading spinner, while staying correct.

**Status:** design approved by the owner 2026-08-21. NOT implemented.

**Architecture:** an in-memory LRU cache in the web app, keyed on the query identity minus the refresh counter. A cache hit paints immediately and then revalidates in the background; the server already answers `304` with an empty body when nothing changed, so revalidation is nearly free. Adjacent days are prefetched quietly so the first chevron click is instant too.

**Tech Stack:** React 19, Vite 6, plain ES modules, `node --test`.

## Why this is needed

Every date change refetches over the network and shows the loading dim. The server caches and ETags the response, so an unchanged day already returns `304`, but the client throws its copy away on every navigation and therefore always pays a round trip with a visible spinner.

## The one non-obvious constraint

Past dates are NOT frozen the moment they end. `revalidateOrientation` (`src/link.js`) re-checks a rolling **30-day** window on every link pass and can flip a fixture's sides, and the results settle pass re-polls up to `RESULTS_MAX_AGE_DAYS` (7) days back. That is why the design revalidates every hit instead of trusting past dates outright. Do not "optimize" that away.

    c.set('a', 1);
    assert.equal(c.get('a'), 1);
    assert.equal(c.has('a'), true);
    assert.equal(c.has('b'), false);
    assert.equal(c.get('b'), undefined);
    assert.equal(c.size(), 1);
});

test('makeLruCache evicts the oldest entry past the cap', () => {
    const c = makeLruCache(2);
    c.set('a', 1); c.set('b', 2); c.set('c', 3);
    assert.equal(c.size(), 2);
    assert.equal(c.has('a'), false);
    assert.equal(c.has('b'), true);
    assert.equal(c.has('c'), true);
});

test('makeLruCache treats a read as recent use', () => {
    const c = makeLruCache(2);
    c.set('a', 1); c.set('b', 2);
    c.get('a');           // 'a' is now the most recent, so 'b' is next out
    c.set('c', 3);
    assert.equal(c.has('a'), true);
    assert.equal(c.has('b'), false);
});

test('makeLruCache overwrites in place without growing', () => {
    const c = makeLruCache(2);
    c.set('a', 1); c.set('a', 2);
    assert.equal(c.size(), 1);
    assert.equal(c.get('a'), 2);

test('makeLruCache supports delete and clear', () => {
    const c = makeLruCache(3);
    c.set('a', 1); c.set('b', 2);
    c.delete('a');
    assert.equal(c.has('a'), false);
    c.clear();
    assert.equal(c.size(), 0);
});

test('makeLruCache tolerates a silly cap', () => {
    const c = makeLruCache(0);
    c.set('a', 1);

- [ ] **Step 3: Write the implementation**

Create `web/src/recordsCache.js`:

```js
// In-memory records cache behind instant date navigation.
//
// Pure and DOM-free so it can be unit tested offline, and so the fetch effect
// in App.jsx stays readable. Holds parsed response bodies, which run to a few
// MB each on a busy day, hence the small default cap.
//
// NOTE ON THE KEY: it deliberately does NOT include the refresh counter that
// App.jsx puts in its effect identity. That counter bumps on every background
// auto-refresh, so including it would mint a fresh slot every few minutes and
// the cache would never hit. Excluding it means an auto-refresh reuses the
// same slot and simply replaces its contents.

// Providers are sorted so that the same selection in a different order is the
// same request, which it is on the wire.
export function recordsCacheKey({ date, filtersKey, completed, providers, token } = {}) {
    const p = Array.isArray(providers) ? [...providers].sort().join(',') : '';
    return [
        date ?? 'all',
        filtersKey ?? '',
        completed === false ? '0' : '1',
        p,
        token ?? '',
    ].join('|');
}

// Insertion-ordered Map used as an LRU: re-inserting on read moves an entry to
// the end, so the first key the iterator yields is always the least recently
// used one.
export function makeLruCache(max = 8) {
    const cap = Number.isFinite(max) && max > 0 ? Math.floor(max) : 1;
    const m = new Map();
    return {
        has: k => m.has(k),
        get(k) {
            if (!m.has(k)) return undefined;
            const v = m.get(k);
            m.delete(k);
            m.set(k, v);
            return v;
        },
        set(k, v) {
            if (m.has(k)) m.delete(k);
            m.set(k, v);
            while (m.size > cap) m.delete(m.keys().next().value);
        },
        delete: k => m.delete(k),
        clear: () => m.clear(),
        size: () => m.size,
    };
}
```

(c) In the existing records fetch effect (currently around lines 670-705), the effect
already builds `queryKey` and guards on `lastQueryRef`. Leave all of that alone.
Add the cache around the fetch:

```js
        const cacheKey = recordsCacheKey({
            date: date || 'all',
            filtersKey: serverFiltersKey,
            completed: showCompleted,
            providers: reqProviders,
            token: session?.token ?? '',
        });
        // Paint from cache first. A revisited date must never show the loading
        // dim: we still revalidate below, and the server answers 304 with an
        // empty body when nothing moved, so correctness costs one small round
        // trip rather than a visible stall.
        const cached = recordsCache.get(cacheKey);
        if (cached) {
            setResult(cached);
            setError(null);
            setSignInNeeded(false);
        }
        if (!silentRef.current && !cached) setLoading(true);
        fetchRecords({ date: date || 'all', filters: serverFilters, completed: showCompleted, providers: reqProviders })
            .then(res => {
                recordsCache.set(cacheKey, res);
                if (current()) { setResult(res); setError(null); setSignInNeeded(false); }
            })
            .catch(e => {
                if (!current()) return;
                // A failed revalidation of data we are already showing must not
                // replace the table with an error. Keep the cached view.
                if (cached && !(e?.status === 403 && e?.body?.auth_required)) return;
                if (e?.status === 403 && e?.body?.auth_required) { setResult(null); setSignInNeeded(true); recordsCache.delete(cacheKey); }
                else setError(String(e.message ?? e));
            })
            .finally(() => { if (current()) { silentRef.current = false; setLoading(false); } });
```

Note the existing `if (!silentRef.current) setLoading(true);` line becomes
`if (!silentRef.current && !cached) setLoading(true);`. That single change is what
removes the spinner.

(d) Add a prefetch effect AFTER the records effect. `PREV_DATE`, `NEXT_DATE`,
`MIN_DATE` and `MAX_DATE` are already computed in this component (around line 1148).
Because they are declared later in the component body than this effect, reference
them inside the effect callback only, never in the dependency array evaluation order,
and include them in the deps:

```js
    // Quietly warm the neighbouring days so the first chevron click is instant
    // too, not just the second visit. Strictly best effort: a prefetch failure
    // is swallowed whole, never surfaces a banner, and never touches table
    // state. Bounded by the same limits the chevrons themselves enforce, so a
    // guest can never trigger a future-date 403 here.
    useEffect(() => {
        if (!date || loading || maintActive) return;
        let cancelled = false;
        const warm = day => {
            if (cancelled || !day || day < MIN_DATE || day > MAX_DATE) return;
            const key = recordsCacheKey({
                date: day,
                filtersKey: serverFiltersKey,
                completed: showCompleted,
                providers: reqProviders,
                token: session?.token ?? '',
            });
            if (recordsCache.has(key)) return;
            fetchRecords({ date: day, filters: serverFilters, completed: showCompleted, providers: reqProviders })
                .then(res => { if (!cancelled) recordsCache.set(key, res); })
                .catch(() => {});
        };
        // One tick after paint, so warming never competes with the day the user
        // is actually looking at.
        const id = setTimeout(() => { warm(PREV_DATE); warm(NEXT_DATE); }, 400);
        return () => { cancelled = true; clearTimeout(id); };
    }, [date, loading, maintActive, serverFiltersKey, showCompleted, providerKeys, session?.token, PREV_DATE, NEXT_DATE, MIN_DATE, MAX_DATE]);
```

If `PREV_DATE`/`NEXT_DATE`/`MIN_DATE`/`MAX_DATE` turn out to be declared below this
effect in a way that breaks (a temporal dead zone error at effect-run time would be
visible immediately in the browser console), MOVE those four `const` declarations up
to just above the records fetch effect rather than duplicating the date maths. Do not
write a second copy of the bounds.
